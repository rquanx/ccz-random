# 统计模块规格说明

状态：Implemented
版本：1.3
日期：2026-10-01
适用版本：3.2.2 及后续版本

## 1. 目标与范围

统计模块用于回答两个问题：

1. 用户最终随机保存了什么结果。
2. 长期运行后，兵种、特技和宝物的分布规律是什么。

统计界面只展示业务结果，不展示 Worker、调度、CPU、内存、注入、阶段耗时等技术信息。技术诊断继续写入现有日志。

统计数据必须来自统一的结构化结果快照，不得从结果图、控制台文字或截图反向识别。

## 2. 统计口径

统计口径和规则维度是两个相互独立的筛选轴：

- 统计口径决定统计哪些结果：最终结果、全部已完成、全部尝试。
- 规则维度决定按哪些规则配置取数：当前规则、指定规则、全部规则汇总、全部规则分组。

因此用户可以不区分规则查看全部规则总体，也可以指定一个或多个规则配置，
或按规则分组并列查看。规则维度不会改变统计口径。

### 2.1 最终结果

默认口径。只统计已通过评分、已由游戏确认保存、并且已成功发布到真实结果存档目录的结果。

判定条件：

```text
status = accepted
save_confirmed = true
published = true
```

同一个运行、轮次和存档只保留一条最终结果。循环模式中，中间轮次结果不进入默认历史统计，除非该结果被标记为最终保留结果。

### 2.2 全部已完成结果

统计已经完成评分并产生结构化详情的结果，包括合格和不合格结果，但不包含只完成部分流程、没有评分详情或已经停止的任务。

```text
scored = true
```

该口径用于比较随机过程中的结果分布，不代表真实保存结果。

### 2.3 全部尝试

统计每一次随机尝试，包括评分不合格、读取失败、保存失败、结果生成失败和其他异常。

每次尝试必须有独立的 `attempt_id`，不能用存档编号代替。一个存档刷 30 次时，全部尝试口径应统计 30 条尝试，但最终结果口径最多统计 1 条。

## 3. 内部状态

数据库内部使用稳定英文枚举，显示层再映射为中文：

| 内部状态 | 显示名称 | 是否计入最终结果 |
| --- | --- | --- |
| `accepted` | 合格 | 是，需同时满足保存和发布确认 |
| `rejected` | 不合格 | 否 |
| `saving` | 保存中 | 否 |
| `saved` | 已保存 | 视发布确认而定 |
| `failed` | 异常 | 否 |
| `stopped` | 已停止 | 否 |
| `unfinished` | 未完成 | 否 |

异常原因单独保存，不通过状态字符串表达：

```text
job_rejected
skill_rejected
load_failed
save_failed
game_exited
result_render_failed
memory_read_failed
enum_unmatched
unknown
```

## 4. 数据模型

继续使用现有 SQLite 数据库 `ccz_fast_data/history.sqlite3`，不新增独立数据库。

### 4.1 runs

一次用户点击“开始随机”到流程结束的运行。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | TEXT | 运行稳定 ID，主键 |
| `run_key` | TEXT | 稳定外部 ID |
| `started_at` | TEXT | 开始时间 |
| `finished_at` | TEXT | 结束时间 |
| `status` | TEXT | `running/completed/stopped/failed` |
| `mode` | TEXT | `three/seven` |
| `loop_enabled` | INTEGER | 是否循环 |
| `rule_name` | TEXT | 规则名称 |
| `rule_id` | TEXT | 稳定规则 ID |
| `rule_schema_version` | TEXT | 规则结构版本 |
| `rule_snapshot_hash` | TEXT | 规则配置指纹 |
| `rule_json` | TEXT | 运行时规则快照；数据库实际字段名 |
| `build_json` | TEXT | 工具版本和构建信息 |

### 4.2 rounds

一次循环轮次。非循环运行也必须创建一个轮次，统一查询逻辑。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER | 主键 |
| `run_id` | INTEGER | 所属运行 |
| `round_number` | INTEGER | 轮次，从 1 开始 |
| `started_at` | TEXT | 开始时间 |
| `finished_at` | TEXT | 结束时间 |
| `status` | TEXT | `running/completed/stopped/failed` |
| `result_count` | INTEGER | 本轮目标存档数 |

### 4.3 attempts

一次存档的一次随机尝试。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER | 主键 |
| `round_id` | INTEGER | 所属轮次 |
| `slot` | INTEGER | 存档编号 |
| `attempt_number` | INTEGER | 该存档本轮第几次尝试 |
| `status` | TEXT | 见内部状态 |
| `failure_reason` | TEXT | 失败原因 |
| `scored` | INTEGER | 是否完成评分 |
| `save_confirmed` | INTEGER | 是否通过游戏保存确认 |
| `published` | INTEGER | 是否发布到真实结果目录 |
| `is_final_result` | INTEGER | 是否为最终保留结果 |
| `created_at` | TEXT | 创建时间 |
| `completed_at` | TEXT | 完成时间 |
| `snapshot_json` | TEXT | 完整结构化结果快照 |

`run_id` 通过 `rounds.run_id` 关联，不在 `attempts` 重复保存。查询层统一通过
`attempts -> rounds -> runs` 取得运行和规则信息，避免两个运行来源不一致。

尝试记录必须幂等更新：

- `(round_id, slot, attempt_number)` 唯一。
- 同一尝试的后续阶段更新同一条记录，不能重复插入。
- 只有评分、游戏保存确认和发布确认全部完成后，才能设置
  `is_final_result = 1`。
- 一个 `(run_id, round_id, slot)` 最多一条最终结果。
- 结果图生成失败不能抹掉已确认的存档结果，应单独记录
  `result_render_failed`。

### 4.4 result_members

从结果快照展开的武将位置，便于统计查询。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `attempt_id` | INTEGER | 所属尝试 |
| `position` | INTEGER | 武将位置 |
| `member_id` | TEXT | 稳定武将 ID |
| `member_name` | TEXT | 当时显示名称 |
| `job_id` | TEXT | 稳定兵种 ID |
| `job_name` | TEXT | 当时显示名称 |
| `job_known` | INTEGER | 是否成功匹配 |
| `personal_skills_json` | TEXT | 原始个人天赋数组快照 |
| `job_skills_json` | TEXT | 原始兵种技能数组快照 |
| `memory_read_status` | TEXT | 内存读取状态 |

一个武将的多个个人天赋必须完整保存，禁止只保留第一项。

### 4.5 result_treasures

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `attempt_id` | INTEGER | 所属尝试 |
| `member_position` | INTEGER | 装备武将位置 |
| `treasure_id` | TEXT | 稳定宝物 ID |
| `treasure_name` | TEXT | 当时显示名称 |
| `properties_json` | TEXT | 宝物特性数组 |
| `set_ids_json` | TEXT | 已识别套装或组合 ID |
| `known` | INTEGER | 是否成功匹配 |

没有真实组合时不生成“特殊组合”空记录。

### 4.6 结果技能与特性索引

`result_members` 中的 JSON 是原始快照，统计聚合不得依赖逐行解析 JSON。需要增加展开索引表：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `attempt_id` | INTEGER | 所属尝试 |
| `member_position` | INTEGER | 武将位置 |
| `skill_scope` | TEXT | `personal/job` |
| `skill_id` | TEXT | 稳定特技 ID，可为空 |
| `skill_name` | TEXT | 当时显示名称 |
| `known` | INTEGER | 是否成功匹配 |
| `is_empty_marker` | INTEGER | 是否为“无天赋/无技能”占位项 |

宝物特性也应有对应的展开索引，或采用等价的规范化表结构。原始快照和数组 JSON 始终保留，索引表作为查询投影。

建议的宝物特性索引字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `attempt_id` | INTEGER | 所属尝试 |
| `member_position` | INTEGER | 装备武将位置 |
| `treasure_id` | TEXT | 稳定宝物 ID |
| `property_id` | TEXT | 稳定特性 ID，可为空 |
| `property_name` | TEXT | 当时显示名称 |
| `known` | INTEGER | 是否成功匹配 |
| `is_empty_marker` | INTEGER | 是否无特性 |

建议建立以下索引：

```text
attempts(run_id, round_id, slot, is_final_result)
attempts(rule_snapshot_hash, status, is_final_result)
attempts(created_at)
result_members(member_id, job_id)
result_skills(skill_scope, skill_id, known)
result_treasure_properties(property_id, known)
```

## 6. 统计范围

筛选器统一适用于四个 Tab：

```text
统计范围：当前运行 / 当前轮次 / 全部历史
数据口径：最终结果 / 全部已完成 / 全部尝试
随机模式：全部 / 初始 3 人 / 完整 7 人
规则配置：当前规则 / 指定规则 / 全部规则汇总 / 全部规则分组
存档范围：全部 / 单个存档 / 存档区间
武将：全部 / 指定武将
时间：全部 / 今天 / 本周 / 本月 / 自定义
```

查询规则：

- `当前运行` 使用当前 `run_id`。
- `当前轮次` 使用当前 `round_id`。
- `全部历史` 默认排除中间轮次，使用 `is_final_result = 1`。
- 用户选择“全部已完成”或“全部尝试”时，允许查看中间轮次，但界面必须显示当前口径。
- 不同规则配置默认不得隐式合并统计。
- “当前规则”只统计与当前规则快照完全一致的历史记录。
- “指定规则”按规则配置快照筛选，不能只按规则名称筛选。
- “全部规则汇总”允许跨规则合并查看总体样本，但必须显示规则数量、样本数量和“跨规则汇总”标识。
- “全部规则分组”按规则配置独立显示，不能生成混合排行榜。
- 3 人模式只统计实际检查的初始 3 个武将位置。
- 7 人模式统计实际完成检查的 7 个武将位置。
- 未完成位置不进入兵种分母。

规则名称不是稳定的统计标识。规则配置必须同时保存：

```text
rule_id
rule_name
rule_schema_version
rule_snapshot_hash
rule_json
```

同名但分数、匹配类型、开关或限制条件不同的规则，必须视为不同统计分组。
统计页面需要显示规则名称、规则版本和配置指纹。

`rule_snapshot_hash` 使用规则配置规范化 JSON 的 SHA-256 计算：

- 对象键按稳定顺序序列化。
- 数组默认保持业务顺序；只有规则 schema 明确声明为无序集合时，才按稳定
  ID 排序后再计算。
- 不包含保存时间、界面展开状态等非规则字段。

规则 schema 必须明确哪些数组是有序配置、哪些数组是无序集合。通用哈希函数
不能猜测数组语义，否则同一规则可能产生不稳定的配置指纹。

规则筛选的默认值为“全部规则汇总”，页面必须持续显示“跨规则汇总”标识。

没有当前运行上下文时，“当前运行”和“当前轮次”应置灰或明确提示不可用，
不能默认为最近一次运行。

规则筛选和统计口径的组合示例：

| 规则维度 | 统计口径 | 含义 |
| --- | --- | --- |
| 全部规则汇总 | 最终结果 | 所有规则最终发布成功结果的总体分布 |
| 当前规则 | 全部已完成 | 当前规则下已经评分的合格和不合格结果 |
| 指定规则 | 全部尝试 | 选定规则配置下的每一次尝试，包括失败和异常 |
| 全部规则分组 | 最终结果 | 每个规则配置分别统计，不混合分母 |

## 7. 指标定义

### 7.1 总览指标

| 指标 | 定义 |
| --- | --- |
| 统计存档数 | 过滤结果涉及的不同 `run_id + round_id + slot` 数 |
| 已完成数 | `scored = 1` 的不同存档任务数；不是尝试记录数。明细和分布在“全部已完成”口径下仍保留每一条已评分尝试 |
| 合格数 | `status = accepted` 且保存、发布均确认的不同存档任务数 |
| 不合格数 | 完成评分但未通过规则的不同存档任务数 |
| 异常数 | 存在最终 `failed` 状态的不同存档任务数 |
| 已停止数 | 存在最终 `stopped` 状态的不同存档任务数 |
| 未完成数 | 没有最终状态或最终状态为 `unfinished` 的不同存档任务数 |
| 合格率 | `合格数 / (合格数 + 不合格数)` |
| 总尝试次数 | 全部 `attempts` 记录数 |
| 平均尝试次数 | 当前筛选范围内的尝试次数 / 不同存档任务数 |

“不同存档任务”使用 `(run_id, round_id, slot)` 去重；不能把同一存档的
多次尝试直接累加为多个已完成存档。总览中的状态统计必须先按存档任务确定
最后一次有效状态，再进行计数；失败原因和“全部尝试”明细则按尝试记录计数。
因此，“全部尝试”口径下总览的状态卡片不是失败原因次数的替代品，失败原因图
才表示每次尝试的累计次数。

异常、已停止和未完成不进入合格率分母。

### 7.2 兵种占比

兵种统计分母必须按武将位置计算：

```text
兵种出现次数 / 已统计的武将位置总数
```

必须同时显示：

- 出现次数
- 出现占比
- 覆盖存档数
- 覆盖武将数
- 分母位置总数

### 7.3 个人天赋

每个天赋数组元素独立计数：

- 天赋出现次数
- 覆盖存档数
- 覆盖武将数
- 按武将分布
- 完整天赋组合

“无个人天赋”作为独立类别，不得静默丢弃。

### 7.4 兵种技能

统计：

- 技能出现次数
- 覆盖兵种数
- 覆盖武将数
- 覆盖存档数
- 按兵种和武将筛选

“无兵种技能”作为独立类别。

### 7.5 宝物

分别统计：

1. 宝物名称。
2. 宝物特殊特性。
3. 已识别套装或特殊组合。

没有真实组合时显示：

```text
本次没有识别到套装组合
```

不显示无信息量的“特殊组合”空栏目。

## 8. 界面规格

统计窗口包含四个 Tab：

```text
总览
兵种分布
特技分布
宝物分布
```

### 8.1 总览

- 汇总数字区。
- 状态饼图：合格、不合格、异常、已停止、未完成。
- 失败原因横向柱状图。
- 历史范围显示趋势曲线。
- 本轮范围显示累计完成数、累计合格数、累计不同结果数。
- 下方显示可筛选明细表。

### 8.2 兵种分布

- 横向柱状图。
- 支持按全部武将、指定武将、指定存档查看。
- 显示次数、比例、分母和覆盖数量。

### 8.3 特技分布

特技必须有两个子 Tab：

```text
个人天赋
兵种技能
```

具体特技使用横向柱状图。特技类别饼图只显示：

- 有个人天赋
- 无个人天赋
- 有兵种技能
- 无兵种技能

### 8.4 宝物分布

- 宝物名称横向柱状图。
- 宝物特性支持环形图和柱状图切换。
- 套装和组合只显示真实识别到的组合。

### 8.5 规则汇总与比较

规则筛选支持四种模式：

- 当前规则：只查看当前正在使用的规则配置。
- 指定规则：选择一个或多个规则配置查看。
- 全部规则汇总：将符合其他筛选条件的所有规则作为一个总体样本查看。
- 全部规则分组：将所有规则分别显示。

“全部规则汇总”适合回答：

- 所有规则下最终保存了哪些兵种。
- 所有历史结果中哪些特技总体出现较多。
- 所有规则运行的总体数量和状态分布。

“全部规则汇总”不适合直接比较不同规则产生的概率差异。页面必须显示：

```text
跨规则汇总
包含规则：N 个
样本数：M 个
```

“全部规则分组”适合回答：

- 不同规则下的结果分布是否不同。
- 某个规则的合格率和平均尝试次数。
- 同一个特技在不同规则下的出现情况。

分组或并列比较时必须显示样本数、统计口径、随机模式和配置指纹。
样本量不足时显示样本不足提示，不得据此得出概率结论。

## 9. 图表交互

所有图表必须与明细联动：

- 点击状态饼图区域，筛选对应状态。
- 点击失败原因柱，筛选对应失败原因。
- 点击兵种柱，显示相关存档、武将和评分详情。
- 点击特技柱，显示拥有该特技的武将和存档。
- 点击趋势节点，显示对应日期或轮次。
- 点击宝物特性，显示对应宝物、武将和存档。
- 点击存档，打开结构化评分详情。
- 点击结果图入口，打开对应结果图。

明细表至少包含：

```text
运行时间
轮次
存档编号
武将
兵种
个人天赋
兵种技能
宝物
宝物特性

```

## 10. 未知项和完整性

未知项必须保留并可筛选：

```text
未知兵种
未知特技
未知宝物
无个人天赋
无兵种技能
无宝物特性
内存读取失败
枚举未匹配
```

统计窗口显示识别概况：

```text
已识别 96 / 105 个武将位置
未识别 9 个
```

图表和明细必须包含未知类别。不能因为未知而减少分母或静默丢弃记录。

## 11. 数据校验

统计查询完成后必须执行以下校验：

1. 兵种条目总数等于已统计武将位置总数。
2. 多天赋条目总数等于所有个人天赋数组元素总数。
3. 宝物特性条目总数等于已识别宝物特性数组元素总数。
4. 未知项包含在对应总数中。
5. 3 人模式和 7 人模式使用正确位置分母。
6. 最终结果口径不重复计算循环中间结果。
7. 合格率分母不包含异常、停止和未完成任务。
8. 技能和宝物特性聚合结果与展开索引表一致。
9. 跨规则汇总的样本数等于各规则分组样本数之和。
10. 总览状态数按存档任务去重，不把同一存档的多次尝试重复计入。
11. 同一尝试的快照、索引和保存/发布状态在更新后保持一致。
12. 规则筛选为空时不把“未知规则”静默归入任意已知规则。

校验失败时：

- 页面显示“数据不完整”。
- 保留可查看的统计结果。
- 显示具体不一致项。
- 不得静默生成看似完整的图表。

## 12. 历史操作与导出

统计模块支持：

- 查看指定运行。
- 查看指定轮次。
- 删除指定运行记录。
- 清空统计历史。
- 从已有快照重新生成统计。
- 导出当前筛选结果。

导出格式：

| 格式 | 内容 |
| --- | --- |
| PNG | 当前图表视图 |
| CSV | 当前筛选后的明细和聚合统计 |
| JSON | 完整结构化结果和筛选条件 |

统计数据分为“结果事实”和“统计投影”。清空统计只清除统计投影或统计隐藏标记，不删除结果事实，不删除：

- 游戏存档。
- `randResult` 结果图。
- 原始运行日志。
- 诊断日志。

清空后仍可以通过“从已有结果重新生成统计”恢复统计。

删除指定运行时，默认删除该运行的结果事实及其统计投影，但仍不删除游戏存档、结果图和日志。删除和清空操作必须二次确认，并明确显示影响范围。

## 13. 查询与服务边界

统计模块分为三层：

```text
SnapshotWriter
    负责运行过程中写入结构化结果

StatisticsRepository
    负责筛选、聚合、校验和导出数据

StatisticsWindow
    负责筛选器、图表、明细和交互
```

UI 不直接拼接 SQL。所有查询由 `StatisticsRepository` 提供参数化方法完成。

建议接口：

```python
get_summary(filters) -> SummaryMetrics
get_job_distribution(filters) -> list[DistributionRow]
get_personal_skill_distribution(filters) -> list[DistributionRow]
get_job_skill_distribution(filters) -> list[DistributionRow]
get_treasure_distribution(filters) -> list[DistributionRow]
get_failure_distribution(filters) -> list[FailureRow]
get_trend(filters) -> list[TrendPoint]
get_detail_rows(filters) -> list[ResultDetailRow]
validate_statistics(filters) -> ValidationReport
export_statistics(filters, format, target) -> Path
```

规则维度应作为独立对象处理，避免 UI 通过字符串拼接 SQL：

```python
RuleScope(
    mode="current" | "selected" | "all_summary" | "all_grouped",
    hashes=tuple[str, ...] = (),
)
```

`all_summary` 返回一个跨规则聚合结果集；`all_grouped` 返回带
`rule_snapshot_hash` 的多个独立结果集。两者必须使用同一基础样本集。

查询服务的结果分为两类：

- 汇总指标：按存档任务去重，适合总览状态、合格率和平均尝试次数。
- 明细/分布指标：按当前统计口径返回尝试或规范化索引行，适合分析每次
  已评分结果和全部尝试。

UI 不得用明细行数反推总览的“统计存档数”，也不得用总览状态数替代失败原因
或技能、宝物特性条目数。

## 14. 兼容与迁移

现有历史记录如果只有旧版 `snapshot_json`：

- 保留原始快照。
- 按可识别字段迁移到新表。
- 缺少的字段填充为未知，不凭空推断。
- 旧记录标记 `schemaVersion = 0`。
- 旧版只有最终结果、没有尝试明细时，只迁移为一条 `legacy_import` 最终尝试，不推断历史失败次数和平均尝试次数。
- 统计界面显示旧数据覆盖范围。

所有时间字段使用带时区偏移的 ISO 8601。日期筛选按应用运行时的本地时区解释。

迁移失败不能阻止工具启动，只能影响对应历史记录的统计，并在统计窗口显示数据不完整。

## 15. 实施阶段与验收标准

### 阶段一：数据基础

实现：

- 运行、轮次、尝试和最终结果关系。
- 统一结果快照。
- 技能和宝物特性的查询索引。
- 个人天赋数组和兵种技能数组。
- 稳定 ID、显示名称和枚举版本。
- 未知项保留。
- 基础完整性校验。

验收：

- 一个存档多次尝试不会污染最终结果统计。
- 一个武将多个天赋不会丢失。
- 3 人和 7 人分母正确。
- 循环中间结果不会进入默认历史统计。
- 同名不同配置的规则不会混合进同一默认统计分组。
- 可以在“全部规则汇总”和“指定规则/规则分组”之间切换，且分母和样本数定义不变。

### 阶段二：基础统计窗口

实现：

- 总览。
- 兵种分布。
- 个人天赋分布。
- 兵种技能分布。
- 宝物名称和特性分布。
- 统一筛选器和明细联动。

验收：

- 修改筛选条件后四个 Tab 同步刷新。
- 图表点击能定位到明细。
- 未知类别可以查看具体存档。

### 阶段三：历史和导出

实现：

- 历史趋势。
- 套装与组合。
- PNG、CSV、JSON 导出。
- 删除指定运行和清空历史。
- 从快照重建统计。

验收：

- 导出内容与页面筛选结果一致。
- 清空历史不影响存档、结果图和诊断日志。
- 删除单次运行不影响其他运行。

### 当前实现边界

截至 2026-10-01，统计数据模型、历史迁移、统一结果快照、三种统计口径、
规则配置筛选与分组、3 人/7 人分母、未知项索引、趋势、识别概况、明细联动、
历史删除/清空/重建以及 CSV/JSON/PNG 导出入口已经实现，并有对应单元测试。

PNG 导出当前是统计窗口视图截图，不是独立图表渲染器；统计窗口使用 Tk
Canvas 的横向柱状图和趋势图，状态分布也以可点击柱状图呈现。

真实游戏运行的统计写入验收仍需在目标设备上执行，不能用单元测试代替。
并发 worker 的共享历史写入已具备单元级隔离测试，但多设备、多 worker、多轮
循环的真实游戏验收仍单独记录，不作为统计查询正确性的前置条件。

## 16. 非目标

本模块不负责：

- Worker 调度监控。
- CPU、内存、进程数和阶段耗时展示。
- 游戏内存地址诊断。
- 结果图 OCR 或反向解析。
- 修改游戏存档。
- 根据统计结果自动修改随机规则。
