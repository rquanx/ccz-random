# 性能测量与第一轮优化（2026-11-10）

## 测量方式

- 使用项目 Windows Python 环境，实际创建 Tk 控件、完成布局并处理事件，不以源码行数推测性能。
- 窗口放在屏幕外测量，替换前台居中定位；结果是内容构建/加载耗时，不是完整 EXE 冷启动或跨设备性能。
- 真实历史库通过只读连接备份到临时目录，再在副本中测量。原库、真实存档与数据包未被修改。
- 使用两组输入：真实历史库（47 轮，最新一轮 1 个结果，详情含 2 名参与评分人物及完整宝物/入队数据）；真实采样夹具（10 轮、每轮 15 个结果，详情含 143 名人物）。
- 每组每项重复 3 次，取中位数。优化前代码在独立诊断进程内重建，未临时回滚用户工作区文件。输入、窗口尺寸、判定条件保持一致。
- “完整加载”表示对应内容全部出现；143 人详情不等于首屏必须等待全体加载。事件延迟通过主线程 8ms 定时探针估计；不把单次 root.update 的总耗时当作一个不可中断回调。

可复测入口：

```powershell
./.venv-win10-py314/Scripts/python.exe -m tools.diagnostics.benchmark_ui
./.venv-win10-py314/Scripts/python.exe -m tools.diagnostics.benchmark_ui --history-db "游戏目录/ccz_fast_data/history.sqlite3" --output artifacts/ui-performance/current.json
```

## 已实施的界面优化

### 详情人物卡片

原实现为每位人物创建 Frame、Label 等完整控件树，143 人详情达到 1,467 个控件。现在使用每人一个 Canvas，保留姓名、兵种/评分、个人天赋、兵种天赋、自动换行和原有配色。

143 人详情：

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 完整加载 | 4,666 ms | 1,453 ms |
| 原生控件数 | 1,467 | 180 |
| 最大事件延迟的中位数 | 2,316 ms | 418 ms |

完整加载约减少 69%，控件数约减少 88%。大规模详情仍有进一步虚拟化的空间，不能视为已消除所有卡顿。

### 宝物列表

同一分类的物品合并到一个多行 Label，不再为每件物品分配一个原生 Label。名称、效果、顺序、分类和特殊组合保留，搜索仍依据原始结构化数据。

真实历史样本：宝物窗口控件数 142 → 83，内容加载 321 → 207 ms；两人详情因同时使用轻量人物卡和宝物布局，内容加载 397 → 238 ms。

### 历史列表

- 历史轮次列表从一次创建整页控件改为分批创建，快速切页时丢弃旧批次。
- 存档摘要卡片从每张固定等待 8ms，改为每批最多 4 张并受 8ms 时间预算限制；绘制开销较大时提前把控制权交还事件循环。
- 保留异步数据库读取、摘要缓存、分页和卡片复用，不改动历史数据库结构。

15 存档/轮的大样本中，历史内容加载 694 → 467 ms，约减少 33%。真实最新轮只有 1 个结果时，完整加载 299 → 316 ms，本次没有测到加速；事件延迟中位数 72 → 48 ms。不能宣称所有历史负载都变快。

### 入队人员

- 确定窗口宽度后再首次绘制，避免先按未布局宽度绘制一遍、再重画。
- 缓存布局条件；宽度、搜索、关卡、特殊技能筛选和特殊技能集合都未变化时不重建 Canvas。
- 筛选防抖从 120ms 降为 50ms；最近搜索的持久化延迟不受影响。

真实历史快照的内容加载 339 → 287 ms；大样本 348 → 322 ms。提升幅度小于详情窗口；首次绘制全部人物卡片仍有开销，若继续优化，优先考虑分批绘制/可视区渲染，而不是减少显示内容。

## 随机流程：瓶颈在哪里

分析了本机及当前游戏目录最近的 20 份既有诊断日志，取具有明确阶段耗时字段的记录，避免混淆全局 elapsed_ms 与阶段覆盖的 elapsed_ms。日志来自既有测试/运行，包含成功、失败和不同启动方式，不能作为本轮优化后新跑出的完整性能认证。

| 阶段 | 样本数 | 中位耗时 |
| --- | ---: | ---: |
| 首次从标题读档 | 14 | 5,744 ms |
| 复用会话、普通菜单读档 | 10 | 3,606 ms |
| 随机交互 | 24 | 1,226 ms |
| 成功 attempt_runner | 22 | 8,610 ms |
| 合格后采集宝物 | 12 | 1 ms |
| 写入历史 | 12 | 22 ms |
| 结果面板生成 | 12 | 65 ms |
| 结果汇总图生成 | 12 | 118 ms |

各行来自不同事件及样本集合，不能直接相加或用中位数相除计算全局占比。

结论：随机核心的主要时间消耗在游戏读档/场景等待和交互。微调历史写入、宝物采集或 Python 名称匹配，不太可能带来同量级的随机吞吐提升。

下一轮值得验证的方向：

1. 把读档拆成菜单交互、存档一致性确认、场景稳定三个可对比阶段，确定 3.6 秒中的可优化部分。
2. 对场景等待研究“明确就绪信号 + 有界超时 + 原等待兜底”，不要直接减掉固定 sleep。旧性能研究已证明部分短等待会失败。
3. 分别测量冷启动、复用、并发 1/2/多实例，以及规则通过率不同的情况，关注单位时间合格结果数、恢复次数和存档一致性。
4. 若合格率高、每个槽位都触发较多重新启动开销，再评估调度器中游戏/Worker 的复用边界；不能假设现有会话复用尚未实现。

本轮没有修改游戏等待、注入、读写存档或随机规则，也没有运行新的真实游戏测速。因此没有“随机流程已提速”的新实测结论。

## 回归与限制

增加回归用例：完整 143 人详情的全部姓名/兵种/天赋保留且控件数量受限；70 件宝物全部保留且控件数量受限；重复尺寸通知不重建人员卡；耗时卡片绘制在数量上限前让出事件循环。

同时修正一个已有历史 UI 用例的等待条件：轮次备注命中应显示该轮所有结果，旧用例只等首张卡出现便断言第二张不存在，实际依赖了慢速分批绘制的中间状态。业务规则已有 test_history_filters 的明确覆盖，未修改筛选规则来迁就测试。

针对性 47 项测试通过；扩大回归后 **645 项测试通过（48.794 秒）**，结果见 `artifacts/ui-performance/regression-tests.txt`。上轮已确认的 3 项 GUI 清理错误单独排除，不应据此写成“全部测试通过”。

测量原始记录：`artifacts/ui-performance/before-mapped.json`、`optimized-mapped.json`、`before-large.json`、`optimized-large.json`、`random-log-analysis.json`。性能会受到 Windows、字体缓存、屏幕缩放、杀毒软件和机器负载影响，以上是本机小样本结果。
