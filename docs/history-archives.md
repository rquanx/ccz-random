# 历史存档与标记

新结果写入历史记录时，会同时把该次游戏实际生成的存档保存在
`ccz_fast_data/history.sqlite3` 的独立存档表中。副本与结果记录在同一事务内提交；
从后台沙箱运行时，读取的是沙箱当前实际存档，不依赖之后同步到游戏目录的文件。
下一次随机覆盖同一游戏槽位、关闭程序或清理残留沙箱，都不影响已经入库的副本。
历史列表只读取摘要和副本是否存在，不加载存档内容。

每张历史卡片的“导出存档”可以取回对应副本，导出前会验证 SHA-256，
通过同目录临时文件原子发布。将导出的文件放回游戏 SV 目录的对应槽位后即可读档；
选择已有目标文件时，文件选择框会要求确认覆盖。

“补备份旧记录”只处理尚无副本的记录。原路径仍存在且 SHA-256 与当时记录相等，
才会保存副本；原文件丢失、被后续随机覆盖或没有校验信息的记录无法补回。
升级数据库不会主动扫描或解码全部旧快照，也不会把当前同槽位文件当成旧记录。

轮次和单个存档均可设置名称、备注及重点标记。搜索同时匹配轮次名称、备注、规则，
以及该轮存档名称和备注；“只看标记”会保留本轮被标记或包含已标记存档的轮次。
名称与备注独立保存，不改变原始人物、评分、宝物快照。

筛选范围以列表所示的本地轮次开始时间为准，可仅填写开始或结束。
支持 `YYYY-MM-DD`、`YYYY-MM-DD HH:MM` 和 `YYYY-MM-DD HH:MM:SS`。
结束日期包含当天，结束时间包含所填的整分钟或整秒。
“今天”“近7天”“近30天”按本地日历日期计算，并与搜索文字、重点标记同时生效；
“重置筛选”清除全部条件。翻页与刷新沿用已应用的条件，不会应用尚未提交的输入。

搜索命中单个存档时，右侧只显示匹配卡片；命中轮次名称、备注或规则时，显示该轮对应存档。
与“只看标记”组合使用时，同一存档需满足全部条件，轮次自身的命名或标记对本轮所有存档生效。
历史列表不再展示状态；数据库内部的轮次状态用于记录任务完成、停止或异常，
与存档合格与否无关。中途停止或异常前已保存的合格存档仍可检索和导出。

删除某轮历史或清空历史会一并删除其独立副本和标记，游戏 SV 目录及旧图片不受影响。
“清空全部历史”包括被筛选隐藏的记录，确认框会明确提示范围。
存储清理里的“历史记录（含存档副本）”同样会删除数据库中的副本。
需要备份或迁移这些历史时，应保留整个 `ccz_fast_data` 目录；复制前先关闭工具及后台任务。

## 并发随机的历史生命周期

并发调度进程统一创建运行和轮次，启动槽位任务前确保对应轮次存在。
单槽位子进程只附着已有轮次、写入结果和存档副本，不改运行配置、结束轮次或清理空轮次。
所有子进程退出后才统一终结运行；已完成轮次保持完成状态，停止时的部分结果继续保留，空轮次才被清理。
兼容模式回退到原目录完整单实例运行时，由该实例正常管理生命周期。

2026-11-10 的循环测试发现旧实现允许任意槽位子进程结束整个共享运行。
多轮交错时，上轮子进程会删除下一轮尚未写出结果的轮次，后续写入触发 SQLite 外键错误。
同时，单槽位进程会错误覆盖共享运行的循环标记。这两项现在由统一生命周期管理规避。

该次测试的四轮归档实际包含 15、15、15、8 个存档，历史只剩 27 条。
补回的 26 条以归档存档前 `0x30000` 字节与故障日志 R0 内存 SHA-256 一致为前提，
再关联同槽位、同尝试的 accepted 详情。恢复后共 53 条及 53 份独立副本，全部与归档哈希一致。
第 4 轮停止后的未生成槽位不属于丢失结果。

## 故障历史恢复工具

`python -m tools.diagnostics.recover_loop_history --help` 查看参数。
默认仅生成 SQLite 一致性备份、恢复预览和计划，增加 `--apply` 才合并到原数据库。
只接受已停止运行；缺失记录必须有日志、归档和哈希匹配的证据，不能根据时间或槽号猜测。
写回前重新核对目标运行和归档未变化，在一个事务内补入缺失记录、摘要和存档副本。
已有记录、备注、标记及其他运行不会被覆盖。
日志未采集的人员详情和个人/兵种特技分类保留未保存标记；原始合格详情与评分按日志恢复。

回归覆盖七个连接跨四轮交错结束、部分轮停止、子进程只读附着、轮次不存在时拒绝写入、
调度完成/停止/异常及子进程数据库路径传递；恢复工具覆盖预览不改原库、原记录保留、
存档副本恢复、哈希不符/非合格/歧义拒绝、历史或归档改变时回滚。
