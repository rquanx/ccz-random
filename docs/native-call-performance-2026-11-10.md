# 内部函数调用与随机性能复查（2026-11-10）

## 已落地的主要改进

上轮把约 2 秒读档开销主要归因于游戏本身，并不准确。本轮逐个测量原生调用后发现：要求 80 ms 的 `wake` 实际耗时约 1510–1530 ms，主要来自持久化通道的请求字段错位。

原生 server 固定读取 `action window x y count right item_index`；旧 Python 编码把 CLI 参数直接依次填入。例如 `wake hwnd 80` 将 80 写到 x，count 仍为零，原生按默认值 Sleep(1500)。`load/save/list` 的槽位、`loadui` 的索引与对象指针、`mouse/event` 的事件参数及定时点击尾等待也有同类错位。原先单测只覆盖无参数 status，无法发现问题。

- 将编码拆为 `runtime/native_protocol.py`，逐动作映射参数字段，校验参数数量。
- 不修改常规和极速策略的点击时序与回退规则；修复二者共用的请求传输，使既有参数按原意生效。
- 原生 injector 增加仅解析的 `--encode-request` 诊断入口，在 OpenProcess 之前返回，不注入或启动游戏。契约测试逐一比较全部 48 个持久化动作的 Python 编码和实际编译的 C CLI 解析结果，覆盖不同参数位置。
- 控制器测试通过真实 stdin 文本验证 wake、loadui、mouse，不再只验证无参数命令。参数缺失、额外参数和非法数字在发送前拒绝。
- 基准增加逐个 native_call 的耗时与动作记录，无新增产品控制台输出。修复后的 80 ms 唤醒实测多数约 97–107 ms（含调度与通信）。

## 直接调用函数的调查结果

这些探针只在完整副本内执行，没有接入正式极速模式。修正协议后重新验证，避免将错误参数误认为游戏内部函数本身的行为。

1. `0x41888D` 底层读档：能恢复部分存档数据，但返回后 state=1、active=1，缺少正常菜单退出后的主循环恢复。极速点击未可靠触发，必须退回常规操作；不能仅凭函数返回成功或 R0 相等就启用。
2. `0x40B84C` 完整对话框加载处理器：选择源槽位并返回后仍处于加载过渡状态。补充正常唤醒后，3 秒内过渡状态仍未归零，因此拒绝该候选方案。旧 loop-load 路线还存在挂起/重入边界，未接入。
3. `0x426075` 游戏内部鼠标输入函数：按移动/按下/放开直接传入事件，但未可靠触发随机，落入常规重试，不计作成功提速。
4. 对 `0x503F40` 兵种字段的真实写入跟踪显示，写入来自脚本解释器（例如 `0x4104E5`），栈上包含多层脚本解释与事件调度；它不是一个可以独立调用、同时完整更新所有随机数据的单一随机函数。只调用底层随机数或字段写入函数，会绕开脚本的其他状态更新。

结论：当前可验证的收益来自修正原生通信协议。直接调用仍有探索空间，但上述候选尚未满足加载过渡完成、稳定随机及存档正确的要求，保持关闭。若继续研究，应找到主循环内正确的完整事件入口，并重复验证源存档、过渡状态、全部人物及存档重启读回，不能只检查三个兵种值。
