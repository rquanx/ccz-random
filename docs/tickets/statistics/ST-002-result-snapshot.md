# ST-002 统一结果快照与运行过程写入

## 目标

建立统一的 `ResultSnapshot`，让内存读取、评分详情、结果图、历史记录和统计模块使用同一份结构化数据。

## 范围

- 定义快照 schema 和版本号。
- 写入完整武将数组。
- 写入个人天赋数组和兵种技能数组。
- 写入宝物、宝物特性和真实套装组合。
- 写入评分、保存确认、发布确认和未知项计数。
- 写入规则 ID、规则快照指纹、规则 schema 版本和完整规则配置快照。
- 同步写入个人天赋、兵种技能和宝物特性的查询索引。
- 在每次尝试、评分完成、最终保存和发布完成时更新记录。
- 支持普通 worker、并发 worker、循环轮次共用同一套写入协议。

## 关键规则

- 多个个人天赋逐项保存，不能只保存第一项。
- 无天赋、无技能、无特性与未知项必须区分。
- 保存失败不能标记为最终结果。
- 结果图只能消费快照，不能重新解析文本。
- 规则名称相同但配置内容不同的结果必须能通过快照指纹区分。
- 原始快照写入失败时不能标记为最终结果。
- 结果保存确认、结果图生成、发布到真实结果目录是三个独立状态；
  结果图生成失败不能回滚已经确认的游戏存档。
- 同一尝试必须使用幂等更新，不能因 `accepted` 回调和结束回调顺序不同
  而把最终结果覆盖成普通不合格尝试。
- 并发 worker 不得自行结束共享运行或轮次；运行协调者负责结束状态。
- 发布确认必须限定到 `run_id + round_id + slot + save_sha256`，不能只按存档号
  更新历史记录。

## 验收标准

- 3 人结果快照包含 3 个实际武将位置。
- 7 人结果快照包含 7 个实际武将位置。
- 一个武将多个天赋全部存在。
- 结果详情和统计读取到的名称、数量与快照一致。
- 内存枚举未匹配时仍保留原始数值、显示名称和 `known = false`。
- 成员、兵种、特技、宝物和宝物特性的稳定 ID、当时显示名称、未知原始值
  均能在快照与索引中对应。
- 并发 worker 先写入未发布结果，协调者真实发布后再更新为最终结果。

## 测试

- 固定内存样本快照测试。
- 多天赋测试。
- 3 人、7 人位置数量测试。
- 未知兵种、特技、宝物测试。
- 保存成功、保存失败和发布失败状态测试。
- 原始快照与技能、宝物特性索引一致性测试。
- 回调重复、回调乱序和发布失败后的状态恢复测试。
- 共享数据库下多个 worker 写入同一运行、不同轮次和不同存档的并发测试。
