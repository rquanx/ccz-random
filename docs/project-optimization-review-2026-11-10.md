# 项目优化梳理（2026-11-10）

## 范围与结论

基于当前工作区（包含未提交改动），检查 Python 正式发布入口、原生控制与调度边界、规则与数据包、历史记录、Tk 弹窗和打包脚本。`src` 下残留的 WPF 构建产物不作为当前发布源码。未执行真实游戏操作、通知发送或线上发布，也未运行 lint、type check、format。

生产 Python 包共 85 个文件、26,558 行；单元测试目录共 67 个 Python 文件，静态发现 644 个测试方法。静态方法数不等于测试实际执行数。

已有较好的基础：随机流程已有独立状态机；并发使用隔离沙箱；历史记录使用 SQLite WAL、分页和摘要；历史弹窗已有异步读取、过期请求隔离及分批绘制；存档导出已有校验和原子替换。因此建议渐进优化，不建议整体重写或迁移 UI 技术栈。

## 优先事项

### 1. P1：让发布脚本精确选择产物和目标游戏

位置：`tools/windows/build_release.ps1:51`、`:60`、`:85`。

现状：构建完成后按整个 dist 目录的修改时间挑选 EXE；未指定 GameDir 时，自动搜索的却仍是 `2.10*.exe`。当前发布名称是 `2.2随机工具.exe`，默认游戏数据已是 2.20-1104夜。本次检查也确认机器上旧 2.10 与新 2.20 游戏目录同时存在。

影响：直接使用脚本默认参数可能把新版工具复制到旧游戏目录。按修改时间选产物也不能严格证明选中了本次构建的目标。

建议：由构建配置明确输出文件名；发布必须指定或从已验证游戏配置确定目录，校验游戏指纹；复制后验证摘要。把最终 EXE 的只读 smoke 检查加入发布流程。不要把真实游戏测试设为普通构建的隐式步骤。

验收：混放多个新旧 EXE、未来时间戳、多个游戏目录时，仍只发布指定产物到指定游戏；不匹配时停止。

### 2. P1：数据包安装需要跨进程隔离

位置：`ccz_randomizer/profiles.py:20`、`:320`。

现状：安装锁是 `threading.Lock`，只覆盖同一进程；临时目录固定为 `.{profile_id}.staging`，安装前会删除该目录。两个独立工具进程更新同一个游戏目录时，不受此锁互斥。

影响：存在一个进程清理或覆盖另一个进程 staging 的竞争窗口。这是代码层面的竞争风险，本轮未通过多进程故障注入复现，不应描述为已经发生的数据损坏。

建议：每次安装使用独立 staging；为目标安装和 active.json 发布增加跨进程锁；竞争失败时保留当前可用版本。继续保持不可变安装目录和原子切换。

验收：两个进程同时安装同包、不同修订，以及其中一个中途退出，最终 active.json 均指向可完整校验的数据包。

### 3. P1：统一异步任务、Tk 回调和关闭清理

位置：`ccz_randomizer/app.py:8733`、`:8798` 附近；可参考 `ui/history_loading.py` 和 `profile_updates.background_call`。

现状：日志上传和兼容性诊断的后台线程直接调用 `root.after`；历史窗口则已经采用队列回传、主线程轮询。多个弹窗的后台任务、定时器和关闭检查实现不一致。

影响：窗口关闭、取消和结果回传之间存在竞争；后台调用 Tk 依赖主线程仍在处理事件。不能把使用 root.after 理解为后台线程完全不接触 Tk。

建议：提取小型任务运行器，工作线程只写队列，Tk 主线程负责回调；任务记录所属窗口、取消信号和请求代次；关闭后丢弃普通 UI 回调，持久化任务按明确策略收尾。

验收：上传期间关闭弹窗、关闭主窗口、立即重开、取消后晚到结果均不报 Tcl 错误、不更新已销毁控件。

### 4. P2：渐进拆分超大函数和运行时补丁

位置：`app.py:8204` 的 gui_main 为 1,796 行；`:6968` 的 patch_runtime 为 1,036 行；`:10002` 的 main 为 1,008 行。`rules/editor.py:821` 的 show_rule_editor 为 1,274 行。

影响：界面、会话、Windows 控制、结果生成和错误恢复仍集中在大闭包内；测试部分依赖局部变量或源代码结构，移动实现容易造成大量无关变动。

建议依次拆出：日志上传与诊断 Controller、结果生成服务、原生控制适配器、游戏会话、规则编辑状态模型。保留兼容入口，每次只迁移一个边界。

设计模式适用点：原生控制用 Adapter；主界面用 Controller；规则/数据读取用显式上下文对象。不要为了模式增加无实际作用的接口层。

验收：单模块能用固定输入测试；拆分前后存档、规则格式和用户可见结果一致。

### 5. P2：数据包激活改用显式快照，降低全局变量耦合

位置：`ccz_randomizer/profile_activation.py:12`。

现状：热激活要更新多个模块的全局变量、环境变量、字典和缓存，还直接操作 `_PINNED_PROFILE_DIRECTORY` 等内部状态。虽然已先进行转换校验，但发布阶段仍是多步修改。

影响：新增一个依赖数据包的模块时容易漏刷新；后续发布步骤异常可能留下部分状态。当前 Worker 固定快照的设计值得保留。

建议：逐步引入只读 ProfileContext，集中保存内存布局、技能、人物和显示规则，消费者通过统一入口获取当前快照；激活时先构造完成，再切换引用并发送一次事件。

验收：新旧 Worker 各自使用完整的一版数据；激活失败保持旧快照；规则编辑未保存内容不丢失。

### 6. P2：降低人员与宝物弹窗重复绘制

位置：`ui/recruitment.py:107`、`ui/equipment.py:76`；可参考 `ui/job_talents.py` 的 last_layout。

现状：人员搜索、规则变化和 Configure 都会清空 Canvas 并重新绘制全部匹配卡片；宝物每次搜索销毁并重建所有子控件。已有 120ms 防抖，但防抖不减少单次渲染成本。

建议先做低成本优化：缓存归一化搜索文本；规则变化才重新计算特殊技能集合；布局和筛选条件未变时跳过刷新；大集合采用分批绘制。仅在实际数据量和测量证明有必要时增加可视区域虚拟化。

验收：使用真实完整快照，记录首次打开、连续输入、窗口拖拽的耗时及响应情况；筛选与红色特殊技能标记仍一致。

### 7. P2：让构建来源可复现、构建标识覆盖数据变化

位置：`packaging/CCZ_真实随机内存快筛版.spec:12`、`packaging/build_metadata.py:28`。

现状：spec 依赖当前机器的绝对路径 `exe-analysis/tool.exe_extracted`。sourceHash 覆盖 Python 源码和部分原生/剧情文件，但没有覆盖打包的数据包 JSON、完整 spec 和全部发布资源。

影响：换电脑构建需要手工补齐隐含依赖；只修改数据包时，sourceHash 不能单独区分两次内容不同的构建。不能将其视为最终 EXE 的完整内容摘要。

建议：运行时依赖用显式配置定位，并在构建开始时校验清单；记录依赖版本和摘要；构建信息包含 profileId、catalogVersion、数据包摘要及打包配置摘要；最终产物继续记录 SHA-256。

验收：在干净目录按文档完成构建；只改一个打包 JSON 时，构建标识或资源摘要随之变化。

### 8. P2：稳定测试环境和窗口定时器清理

本轮先用系统 Python 运行全量测试，633 项中出现 5 个 error：两项模块导入缺少 pycaw/psutil，三项 GUI 用例在销毁窗口时出现 `can't delete Tcl command`。系统 Python 不等于项目打包虚拟环境，因此缺依赖不能归为产品缺陷。

GUI 报错发生在 test_support_ui 和 test_ui_polling 的清理阶段。这些用例会用 root.after_cancel 取消所有窗口的定时器，而状态指示器现在也持有动画定时器，需要进一步验证回调所属控件和测试清理是否一致。当前证据不能证明实际用户关闭软件必然出现相同问题。

项目打包虚拟环境中的针对性复核运行 20 项，结果为 16 项通过、3 项 GUI 清理 error、1 项空间清理显示断言失败。空间清理用例随后在独立进程单独执行通过，提示存在测试顺序或 Tk 共享状态干扰，不能直接认定空间清理功能错误。打包环境不缺 pycaw/psutil；最初完整复核长时间未结束后已停止，没有得到通过结论。

随后在打包虚拟环境中，仅排除已确认报错的上述 3 项 GUI 用例，其他 **641 项测试全部通过，耗时 45.739 秒**。因此当前可复核结论为“641 项通过，3 项已知 GUI 清理问题待处理”，不能写成“全量测试通过”。

建议：统一使用项目虚拟环境作为测试入口；定时器由创建控件负责注销；测试先关闭窗口/Controller，再清理各自的任务，不跨控件取消全部 Tcl 回调。将纯逻辑、Tk 行为、最终 EXE smoke、真实游戏测试分层记录。

详细记录：`artifacts/project-review-unit-tests.txt`、`artifacts/project-review-build-env-tests.txt`、`artifacts/project-review-targeted-tests.txt`、`artifacts/project-review-isolated-tests.txt`。

## 性能优化顺序

随机核心已有低频检查跳过、内存直读、游戏会话复用和动态任务队列。旧性能研究有明确成功率门槛，不建议继续凭感觉缩短固定等待。

先按当前游戏版本重建阶段耗时基线：读档、随机、兵种判定、技能采集、保存、结果图。结合通过率比较“单位时间合格结果数”，不要只比较每次点击耗时；再决定是否调整轮询、复用或批量内存读取。以上候选优化的收益尚未经过本轮真实性能基准验证。

## 建议实施顺序

1. 固定测试环境并解决 GUI 清理错误，建立可信回归基线。
2. 修正发布目标选择、产物选择和摘要校验。
3. 为数据包安装补跨进程测试和隔离。
4. 统一异步任务生命周期，再迁移上传与诊断弹窗。
5. 渐进拆分 app、引入快照上下文；按测量结果优化绘制和随机热点。

本轮只新增审阅文档与本地测试日志，没有修改业务实现，也没有重新发布 EXE。
