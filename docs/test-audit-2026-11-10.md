# 测试审计（2026-11-10）

整改已实施：下面保留初次审计依据，后续调整与验证见文末“整改记录”。

## 范围与结论

盘点 70 个单元测试模块、679 个测试方法，检查高风险流程的断言和正式游戏测试入口，并在独立 Windows 桌面验证测试顺序。游戏 manifest 共 21 项，其中默认回归 11 项、手动诊断 10 项。本轮没有启动真实游戏，没有修改、删除正式 case。

已有大量有价值的行为测试，尤其是规则、并发调度、历史异步加载、安装竞争和窗口关闭。主要问题是测试隔离、旧诊断被当成生产回归，以及极速模式的真实验证尚未成为可重复的正式用例。不能仅根据用例数量或默认顺序全绿认定覆盖充分。

未安装覆盖率依赖，本报告不提供行覆盖率或分支覆盖率。静态盘点的“读取文件/源码”候选包含真实内存样本和 JSON 夹具，不能全部视为无效源码测试。

## 已证实问题

### P1：GUI 测试泄漏游戏版本，导致顺序依赖

位置：`tests/unit/test_ui_polling.py:78`、`:13`，`tests/unit/test_support_ui.py:41`。

临时审计 runner 在每条测试前后比较环境变量，观察到以上三条测试可将 `CCZ_GAME_VERSION` 从未设置变成 `2.20-1104-night`，未恢复。GUI 测试虽然 mock 了 `activate_game_version`，仍有其它初始化路径改变环境。

正确设置子进程导入路径后，逆序运行 679 条：3 个 failure、4 个 error。受影响的旧版人员样本、入队目录和选择人物按钮测试使用了夜版目录或数量。仅在临时 runner 每条测试后恢复环境，逆序结果减少到 1 个 failure，原有 6 项版本相关失败/错误消失。

建议：在涉及 GUI 初始化的测试局部保存并恢复环境；旧版夹具用例显式指定版本，避免依赖当前默认值；对共享目录、缓存、数据快照同样明确初始化和恢复。不要通过固定测试顺序或修改旧版样本预期掩盖问题。

### P1：默认集成 case 可以在随机未成功时通过

位置：`tests/integration_game/cases/case_silent_real_flow.py:22`、`:38`、`:110`。

该 case 仍使用旧读档对话框和硬编码点击坐标，随机后仅打印兵种和状态，没有断言随机成功、规则结果或保存结果。还要求原本存在 SV001，再用 SV020 覆盖它；这并非当前应用的必要前置条件。

建议：移为手动旧引擎诊断，用当前 runner 的端到端 case 替换默认项。新 case 必须在无输入、输入无效、保存失败时失败，验证合格结果和存档读回，不以打印日志代替断言。

### P1：游戏测试清理范围超过自身实例

位置：`tests/integration_game/runner.py:31`、`:200`。

清理通过全系统进程名称枚举所有 Ekd5.exe，再逐个 taskkill。入口开始时检查游戏已关闭，无法保证测试期间用户不会启动自己的游戏；该实例会被误作残留而关闭。这是框架边界问题，本轮没有实际执行杀游戏验证。

建议：统一使用短路径游戏沙箱，登记本次创建的 PID、创建时间、可执行文件位置和进程树，仅清理这些实例；用 Mock 验证陌生 PID、同名进程、PID 复用不会被清理。子进程超时也应按所属进程树清理，并 wait 回收。

### P2：游戏文件恢复范围不构成完整隔离

位置：`tests/integration_game/runner.py:151`，`tests/helpers/game_backup.py:19`。

框架直接向 case 传入所选游戏目录，只备份 `SV/*.E5S` 和 `RS/S_00.eex`。它没有保护根目录 S_00、游戏配置及其它可能修改的文件；部分 case 自行隔离，框架没有统一保证。当前备份测试只覆盖正常退出的还原，未覆盖 case 异常、恢复失败或还原后摘要验证。

建议：优先统一沙箱；保留备份作为额外保障，补异常退出、原文件缺失、新文件清除、恢复失败可诊断等用例，并记录还原后哈希。不能把“有备份”视为整个真实目录都不会变化。

### P2：部分集成用例绕开被测主流程

位置：`tests/integration_game/cases/full_randomizer_normal_load.py:11`、`:70`。

三人/七人 normal-load case 自行复制 trigger_random，直接点击和读内存，没有通过当前 RandomInteractionSession 策略分发。它们适合验证底层读档复位，无法保护主流程策略选择、回退、筛选和保存编排。

建议：保留一个底层读档契约测试；生产回归通过实际 runner 驱动。`randomizer-seven-normal-load` 降为手动兼容诊断，避免默认套件给人仍覆盖当前用户主流程的错觉。

### P2：“不抢前台和鼠标”没有完整对应断言

位置：`tests/integration_game/cases/case_native_ui_load.py:45`、`:57`。

该 case 只比较开始和结束时的前台窗口，没有检查鼠标；中途抢前台后恢复也会通过。框架记录桌面前后状态，但不将变化判为失败。

建议：明确环境约束，在受控桌面监听前台事件、检查测试进程是否获得前台；鼠标位移需排除用户实际操作，不能简单把任何变化归因于工具。无法稳定断言时，应缩小用例名称和说明。

## 建议优先补全

| 层级 | 场景 | 应断言的可观察结果 |
| --- | --- | --- |
| 单元 | GUI 初始化、关闭、重复启动 | 环境和数据版本恢复，旧任务不能向新窗口投递 |
| 单元 | 极速稳定性等待中停止、内存读取失败/短读、进程消失 | 及时终止，不筛选、不保存不完整结果 |
| 单元 | 极速状态由变化退回基线、临界超时、交替快照 | 未稳定结果不可接受，实例回退单向且不影响其它实例 |
| 编排 | 常规/极速分别经过实际适配器、规则拒绝/接受、保存失败 | 两种策略均复用正确规则和保存契约，错误结果不发布 |
| 游戏 | 常规与极速首轮、复用多轮、首次 NPC 输入失效 | 真实主流程完成；极速仅自身回退，后续正常复用 |
| 游戏 | 合格保存后关闭游戏，再启动读取 | 全部参与结果的人员兵种与特技和保存前一致；源 SV020 不变 |
| 游戏 | 读档、稳定性等待、菜单保存、发布阶段分别停止 | 无意外重启；关键保存按约定收尾，结果完整且不重复 |
| 打包 | EXE 单实例、真实双实例、极速和常规混合 | 两个实例确实重叠运行，存档槽位和回退互不串扰 |
| 性能 | 固定数据规模下历史/详情/入队打开和连续筛选 | 主线程可响应、无重复加载/无界控件增长；独立基准记录中位数及 P95 |

极速单元测试目前已经覆盖默认关闭、布尔校验、常规隔离、独立回退、未稳定拒绝、输入前停止等，应保留。缺的是异常边界和实际保存链路，不是完全没有测试。

`tools/diagnostics/benchmark_random_22.py` 已有极速、丢弃首次 NPC、保存等参数，但未注册到正式 manifest。此前真实存档读回和打包冒烟证据值得保留，需把关键断言和夹具迁入可版本管理的测试入口；ignored 临时脚本不能作为干净 checkout 的回归保障。

性能测试不宜在普通单测里硬卡毫秒阈值。普通单测检查批次让出事件循环、缓存命中和任务取消；独立基准固定数据量、机器环境，保存基线和分位数。

## 建议删减、替换与保留

- **替换** `test_session_management.py:697` 的源码 split/assertIn 型流程证明：它可因纯重构失败，也不能证明实际读档行为。补调用实际入口并检查内存结果、异常和停止行为。少量“禁止危险 API”的架构约束可独立保留。
- **增强** `test_project_layout.py:22` 的发布脚本字符串断言：保留 spec 结构约束，但错目标目录、错误产物和失败时不覆盖，应有可执行的临时目录测试。
- **调整** `test_build_info.py:70` 等固定版本号、固定 changelog 条数用例。版本一致性应对比 VERSION 和变更记录，发布版本锁定可放发布检查，避免每次正常发版都改无关测试。
- **降级而非直接删除** 旧七人流程、旧静默流程和重复点击探针；保留诊断用途，移出默认生产回归。
- **保留** `test_workflow.py` 的停止/接受/异常编排、`test_concurrent.py` 的重复结果和关键保存收尾、`test_project_hardening.py` 的真实多进程安装竞争与快照回滚。
- **保留** `test_history_loading.py:109`、`:157` 的慢读取不阻塞、旧请求丢弃和关闭取消；`test_recruitment_ui.py:121` 的特殊技能、搜索、关卡和规则联合筛选。
- **保留并明确版本** 真实人员内存、脚本和保存结果夹具，不要因当前默认版本升级就删掉旧版本回归。
- **无需因没有 assert 就删除** `test_audio_attack_benchmark.py:46`、`:70`。这两条验证合法数据不被 validator 错误拒绝，配套已有非法输入抛异常测试。

未发现同一个测试类内重复 test 方法名导致静默覆盖。没有证据支持按数量大规模删除 case。

## 整改记录

- 当前为 72 个单测模块、692 条测试（新增 15 条，合并或删除 2 条）；游戏 manifest 为 24 项，默认 10 项，手动诊断 14 项。
- GUI 测试自行保存/恢复环境，旧版夹具明确绑定 2.2；没有靠固定排序掩盖泄漏。
- 正式单测入口使用独立 Windows 桌面。严格 runner 将环境泄漏、线程异常、Tk 回调异常和析构异常计为失败，并在主线程回收 Tk 循环对象。新增基础设施测试验证这些异常真的会使测试失败。
- 热激活子进程在局部作用域管理窗口，先销毁控件并在 Tcl 存活期间回收，再销毁根窗口；增加超时和固定 cwd。最终正常顺序与逆序未再复现之前的原生退出异常。
- 游戏 case 改用短路径完整副本，不对源游戏建立硬链接。Windows Job 在运行 case 前登记所属进程，限制清理范围并处理超时后代进程。已用真实临时 Python 进程验证孤儿清理、非游戏后代清理和陌生进程存活，不启动游戏。
